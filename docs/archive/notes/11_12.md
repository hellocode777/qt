这两层（**Layer 11: Monitoring Layer** 与 **Layer 12: Knowledge Layer**）处于你 12 层量化架构的**最顶层与最底层“闭环”处**。

如果说前 10 层解决了“如何产生 Alpha”和“如何执行交易”的问题，那么：

* **Layer 11（监控与熔断）** 解决的是 **“系统今天还活着吗？策略有没有失效？”** 的实时生存问题。
* **Layer 12（知识与归因库）** 解决的是 **“系统如何从失败中学习？策略进化资产如何沉淀？”** 的长期进化问题。

结合你刚刚确立的 **《V2.1 交易宪法》**（Stateless Decision、Risk First、Multi-tagging 归因），这两层的设计必须**极度客观、数据驱动**，不给主观情绪留任何摇摆空间。

## Layer 11: Monitoring Layer（监控与熔断层）

这一层相当于量化平台的 **“ICU 监护仪 + 自动灭火器”**。它的核心职责是**在策略衰退（Decay）或市场环境剧变（Regime Shift）时，自动接管控制权，防止出现巨额回撤**。

### 1. 核心三大模块设计

#### (1) Drift & Decay Detection（漂移与衰退检测）

策略失效通常有两种形式：**突然暴毙（Data Drift）** 或 **慢性死亡（Alpha Decay）**。

* **数据/特征漂移（Data/Feature Drift）**：
* **监控指标**：计算近 30 天输入特征（如换手率、量价因子）与训练集特征分布的 **PSI（Population Stability Index，总体稳定性指标）** 或 **KS 检验值**。
* **触发动作**：当 $PSI > 0.25$ 时，说明市场特征分布已与模型训练时发生严重偏移，系统自动发出警告：`Data Shift High -> Request Retrain`。


* **Alpha 衰退（Alpha Decay）**：
* **监控指标**：计算滚动 20 日/60 日的 **IC（Information Coefficient，信息系数）** 和 **Rank IC**，以及 IC 的 Sharpe 比率。
* **触发动作**：若 Rank IC 连续 20 个交易日均值低于 0.02（或显著低于历史基线），触发 Alpha 衰退预警，自动降低该 Strategy Engine 的目标权重。



#### (2) Market Regime Engine（市场状态/环境引擎）

市场不是匀速运转的，动量策略在牛市/震荡市表现极佳，但在**极端流动性危机或剧烈 Style Switching（风格切换）** 时容易吃大亏。

* **状态分类**：通常将市场划分为 4 种状态：
1. `BULL_TREND`（高动量、低波动）：Alpha 最佳发挥期，按标准规则运行。
2. `HIGH_VOLATILITY`（高波动、极剧烈）：缩减整体仓位，扩大 Buffer。
3. `LIQUIDITY_CRUNCH`（流动性危机）：冻结买入，禁止新建仓。
4. `STYLE_REVERSAL`（风格剧烈反转，如极速微盘杀/高低切换）：暂停排序驱动，提升现金比例。


* **输入数据**：大盘指数波动率（VIX / 历史波动率）、全市场涨跌停家数比、量能突变率、行业轮动速度（Sector Rotation Speed）。

#### (3) Kill Switch（策略熔断机制）

熔断是**独立于单股止损（-10%）之外的“组合级保命阀门”**。

```python
class KillSwitchLevel(Enum):
    NORMAL = "NORMAL"          # 正常运行
    WARNING = "WARNING"        # 警告：限制新建仓，降低杠杆/仓位上限
    HALT_BUY = "HALT_BUY"      # 暂停买入：允许卖出/止损，禁止新增 Buy Order
    FULL_STOP = "FULL_STOP"    # 紧急熔断：全盘清仓，锁定交易接口

```

* **熔断触发条件（Hard Rules）**：
* **组合回撤（Portfolio Drawdown）**：周回撤 $> 5\%$ 触发 `HALT_BUY`；月回撤 $> 10\%$ 触发 `FULL_STOP`。
* **连续亏损日数**：连续 5 个交易日日度 PnL 为负，触发 `WARNING` 并强制人工复核。
* **异常换手率/交易异常**：单日产生的 Trade Recommendations 超过总持仓数的 80%（防代码 Bug 导致的疯狂换手），直接触发 `FULL_STOP`。

## Layer 12: Knowledge Layer（知识与资产库）

很多个人量化开发者做几年后，发现手头只有一堆乱七八糟的代码和未整理的 Excel。**Layer 12 的本质是“量化研究的复利数据库”**，把每一次失败、每一个环境变化、每一次人机决策转化为可检索的资产。

### 1. 核心四大资产库设计

#### (1) Failure Archive（失败档案库）

**“量化系统是通过死掉的策略滋养出来的。”** 这个库专门收集系统暴雷或不达预测预期的数据样本。

* **记录内容**：
* 每次触发 `Stop Loss`（-10%）的股票名单及其买入时的特征快照（Feature Snapshot）。
* 触发 `Kill Switch` 的市场背景与归因。


* **长期价值**：定期在 Failure Archive 上运行聚类分析（Clustering），找出“模型最容易踩坑的股票特征分类”（例如：高负债率+突发高换手的次新股），直接反哺给 Layer 2/3 作为**全局黑名单规则（Negative Screening）**。

#### (2) Research Debt（研究债务与 Iteration Log）

记录你在开发过程中“知道有问题但暂时没时间优化”的待办事项，以及策略版本的演进历史。

* **记录内容**：
* **策略版本树**：V1.0 (基础多因子) -> V2.0 (LightGBM 排序) -> V2.1 (加入 Hysteresis Buffer)。
* **研究债务清单**：例如 *“当前未考虑尾盘 15 分钟跳水对 IC 的影响，待加入 Tick 级高频微观结构特征”*。


* **长期价值**：避免未来的你重蹈覆辙，重复开发曾经证明无效的因子或想法。

#### (3) Market Regime Notes（市场宏观/微观日志）

将市场历次重大波动与策略表现进行“交织对齐”。

* **记录内容**：
* 2024年2月微盘股流动性危机发生时，模型的排名输出表现如何？
* 2024年9月底暴涨行情中，Hysteresis Buffer（Top 10 -> Top 20）是否有拉低收益？


* **长期价值**：为 Layer 11 的 Market Regime Engine 提供历史标注样本（Ground Truth Data）。

#### (4) Decision Audit & Trade Reason Log（决策审计与原因日志）

完美契合你《V2.1 宪法》中 **“保留多个 Exit Reason”** 的原则。

* **记录内容**：
* 每日 `Strategy Engine` 输出的 Raw Target Portfolio。
* 每日 `PM` 和 `Risk Engine` 最终生成的 `Trade Recommendations`，附带完整 Tag（`STOP_LOSS`, `RANK_DROP`, `RISK_EVENT`）。
* **人类决策记录（Human-in-the-loop Log）**：投资者是否覆盖（Override）了系统的建议？覆盖原因是什么？（如：*人工否决了某只股票的买入，因为盘后发布了减持公告*）。

## 两层之间的联动与系统闭环

这两个顶层模块不是孤立存在于 UI 看板上的，它们在底层通过**数据流形成了闭环**：

```
                      ┌────────────────────────────────────────┐
                      │    Layer 11: Monitoring Engine         │
                      │  (Drift / Regime / Kill Switch)        │
                      └──────────────────┬─────────────────────┘
                                         │  触发事件 / 熔断快照
                                         ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│                    Layer 12: Knowledge & Archive Store                       │
│                                                                              │
│  [ Failure Archive ]   [ Market Regime Notes ]   [ Decision Audit Log ]      │
└────────────────────────────────┬─────────────────────────────────────────────┘
                                 │
                                 │ 归因分析 & 数据反哺
                                 ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│                   反哺给下游/基础层 (Continuous Improvement)                 │
│  -> 反哺 Layer 2 (Risk/Blacklist Rules)                                       │
│  -> 反哺 Layer 4 (Feature Engineering - 针对性特征优化)                        │
│  -> 反哺 Layer 8 (Strategy Engine - 模型迭代与重新训练)                        │
└──────────────────────────────────────────────────────────────────────────────┘

```

### 总结：这两层在工程实现上的核心数据表建议

为了在 Python / PostgreSQL / SQLite 中落地，你只需要建 3 张核心表：

1. **`system_health_log`**：记录每日的 Drift PSI、IC 值、Regime 状态、Kill Switch 状态。
2. **`trade_decision_audit`**：记录 T 日生成的建议、Trade Reason Tags、人工审核结果、实际执行价格。
3. **`failure_archive`**：记录所有止损事件、黑天鹅事件发生时的完整因子截面数据。

这样的设计，既保证了 **Layer 11 作为自动守卫** 随时保护资金安全，又保证了 **Layer 12 作为长期大脑** 累积你的量化研究资产，彻底完成你 12 层架构的终极闭环！
